# 从滑块组件到前端安全链路：滑块验证码 SDK 的设计与代码解析

## 前言

很多人提到滑块验证码，第一反应通常是“一个可以拖动的 UI 组件”。但如果真正去拆代码，会发现一个可上线、可交付、可复用的滑块验证码系统，核心难点并不在 UI，而在于它背后的安全链路设计、浏览器兼容、工程化封装，以及如何让业务方以最低成本接入。

这篇文章基于当前仓库做技术拆解，目标不是写一篇营销文，而是尽量从源码出发，把这个项目真正值得讲的关键点梳理清楚。

## 一、这个项目到底是什么

从仓库结构和代码职责来看，这不是一个单一前端页面，而是一个滑块验证码前端 SDK 的 monorepo。

它至少包含下面几层能力：

- **SDK 主包**：负责组件初始化、UI 生命周期、请求链路、回调暴露
- **核心逻辑层**：负责初始化数据处理、验证数据加密、内部状态管理
- **WASM / JS 双实现**：在不同浏览器能力下提供不同核心实现
- **加密兼容层**：现代浏览器优先用 Web Crypto，老浏览器降级到 CryptoJS
- **示例应用**：用于调试、演示和业务接入验证

也就是说，它本质上不是“一个验证码页面”，而是“一套可分发、可复用的前端验证码能力”。

## 二、先看整体架构：为什么它是一个 monorepo

当前仓库用 `pnpm workspace` 管理多个包，主要模块可以这样理解：

- `packages/libs/captcha-sdk`：对外暴露的 SDK 主包
- `packages/libs/captcha-core`：统一的核心能力入口，负责选择 WASM 或 JS 实现
- `packages/libs/captcha-core-wasm`：核心逻辑的 Rust + WASM 版本
- `packages/libs/captcha-core-js`：核心逻辑的纯 JS 回退实现
- `packages/libs/utils-crypto`：加密工具封装，负责 `Web Crypto` 和 `CryptoJS` 兼容
- `packages/libs/captcha-utils`：请求、内部存储等通用工具
- `packages/apps/captcha-sdk-example`：示例应用

这种拆分方式的好处是职责清晰：

1. **业务接入和核心算法解耦**，SDK 主包不需要直接承载所有底层实现细节。
2. **兼容性策略更容易演进**，比如未来替换 WASM 或替换加密实现，只需要改动某一层。
3. **更适合做可交付产品**，而不是只为单个页面做一次性开发。

## 三、完整链路：一次滑块验证在前端是怎么走完的

如果把整个流程压缩成一句话，它做的是：

> 前端先收集设备和会话信息，再收集用户行为，最后把这些数据动态加密后提交给后端验证。

可以把流程理解成下面这条链路：

```mermaid
flowchart LR
  A[业务页面调用 initJmCaptcha] --> B[SDK 初始化 UI 和请求能力]
  B --> C[生成设备指纹]
  C --> D[调用 /captcha/init 获取盐值、时间戳、会话信息]
  D --> E[核心层处理 init 响应并保存内部状态]
  E --> F[用户拖动滑块，采集轨迹]
  F --> G[组合坐标 + 轨迹]
  G --> H[派生动态密钥并加密]
  H --> I[调用 /captcha/verify 提交密文]
  I --> J[业务侧拿到结果，继续调用 /captcha/check]
```

核心入口在 `packages/libs/captcha-sdk/src/index.ts`，这里先预加载核心能力：

```ts
import { getCaptchaCoreApi } from "@captcha/captcha-core";
import initJmCaptcha from "./captcha";

getCaptchaCoreApi();
export default initJmCaptcha;
```

这个设计很像“预热”：在业务真正调用 SDK 之前，先把核心能力准备好，减少首次交互时的等待。

## 四、SDK 主包：它是怎么组织生命周期的

真正的主链路在 `packages/libs/captcha-sdk/src/captcha/index.ts`。

这里最重要的设计点有三个：

### 1. 对外只暴露一个统一入口

业务侧通过 `initJmCaptcha(options)` 获取实例，不需要知道底层到底是 WASM 还是 JS，也不需要直接管理加密器和轨迹模块。

这类封装非常符合 SDK 设计思路：

- **业务方关心的是“怎么用”**
- **SDK 内部自己负责“怎么实现”**

### 2. 单例化降低接入复杂度

代码里用 `instance` 缓存 SDK 实例。如果实例已存在，则重新 `render`，而不是反复新建。

这种方式的好处是：

- 页面集成简单
- 生命周期集中
- `refresh()`、`destroy()` 之类的操作更容易统一管理

它的代价也很明显：

- 如果未来需要同一页面多个验证码实例，单例模式会有扩展压力

这也是一个很好的面试表达点：你不一定非要说它“完美”，而是可以主动讲出它当时为什么这样做，以及未来如果扩展多实例会怎么改。

### 3. SDK 自己把 UI、请求和状态绑在一起

`render()` 里会做几件关键事情：

- 合并和校验配置
- 设置语言
- 配置请求超时
- 创建验证码 UI
- 绑定滑动事件
- 触发初始化逻辑

也就是说，对业务方来说，只需要传容器和回调；剩下的大部分动作都在 SDK 内部完成。

## 五、设备指纹：为什么它是这个项目里的第一层风险信号

设备指纹逻辑在 `packages/libs/captcha-sdk/src/captcha/FingerprintGenerator.ts`。

这里有几个很值得讲的点。

### 1. 使用动态导入，而不是在主包里直接静态打进去

```ts
this._fp = await import(
  /* webpackChunkName: "fp" */ "@fingerprintjs/fingerprintjs"
);
```

这样做的意义是：

- **降低主包首屏体积**
- **把相对重的能力拆成独立 chunk**
- **更适合 SDK 在不同页面场景按需加载**

### 2. 指纹结果做了缓存

`generateFingerprint()` 会把结果存在 `_cache` 里，避免在一次验证码流程里重复计算。

这说明项目在做安全能力的同时，也考虑了性能成本：设备指纹通常不是一个非常轻量的操作，没必要在同一会话里重复生成。

### 3. 指纹不是“唯一判官”，而是链路中的一个输入

`getFingerprintHash()` 返回的 `visitorId` 会进入初始化和验证链路，但它并不是唯一判断条件。这个设计是合理的，因为指纹更适合作为风险因子之一，而不是单独作为通过/拒绝依据。

这点在面试里很重要：如果你说“设备指纹能唯一识别用户”，很容易被追问。更稳妥的说法应该是：

> 设备指纹用于增强会话绑定和风控判断，不单独承担业务裁决。

## 六、轨迹采集：这个项目为什么不只看最终坐标

轨迹采集逻辑在 `packages/libs/captcha-sdk/src/captcha/TrajectoryCollector.ts`。

这部分是项目从“普通组件”变成“安全验证组件”的关键之一。

### 1. 采集的是过程，而不是只采集结果

轨迹数据结构里至少包含：

- `x`
- `y`
- `t`（时间戳）
- `p`（压力占位字段）

也就是说，前端不是只记录“最后停在哪”，而是记录“用户是怎么滑过去的”。

### 2. 对轨迹做了速度与平滑度分析

代码里有两类分析：

- **速度分析**：看平均速度、最大速度、波动程度
- **平滑度分析**：看轨迹拐点和角度变化

这背后对应的思路很典型：

- 真实用户操作不会完全匀速
- 自动化脚本更容易产生机械化、过于规则的轨迹

所以轨迹比“最终 x 坐标”更能提供行为信号。

### 3. 前端已经在做基础分析，但最终可以和服务端风控结合

当前仓库里，轨迹会被组装到 `verificationData` 里并进入加密上报链路。对于安全场景来说，更推荐的做法一般是：

- 前端做基础采集和预处理
- 服务端做最终策略判断

这样更适合后续做风控策略升级，也更不容易被前端静态分析完全绕过。

## 七、动态密钥加密：这是这个项目最核心的设计点之一

如果只用普通 JSON 提交滑块位置，接口非常容易被重放或模拟。所以这个项目把“每次会话动态派生密钥”做成了核心链路。

### 1. 初始化阶段先拿到会话相关材料

`initCaptcha()` 会调用 `/captcha/init`，拿到一组初始化数据，里面至少包括：

- `salt`
- `timestamp`
- `requestId`
- 一个经过加密的 header name

在 JS 核心实现里，`processInitResponse()` 会先把这些数据存进内部存储，再解密出真正的响应头字段名。

这一步有两个目的：

1. **把后续验证所需的材料先准备好**
2. **避免把关键字段名和状态完全直白地暴露在上层业务代码里**

### 2. 验证阶段再按本次会话动态派生密钥

当前仓库的核心逻辑大致是这样：

```ts
const key = await manager.deriveKey(
  fingerprint + salt + timestamp + requestId,
  salt,
  pbkdf2Iterations
);
```

然后再用这个 key 去加密轨迹和坐标：

```ts
const encryptedData = await captchaCoreApi.prepareVerificationData(
  fingerprint,
  JSON.stringify(verificationData),
  PBKDF2ITERATIONS
);
```

这样做的价值非常直接：

- **每次会话的 key 都不同**
- **数据和设备、时间、会话三者绑定**
- **降低请求被抓包后直接复用的风险**

### 3. 内部状态不是简单挂在实例字段上

仓库里有两种状态保存思路：

- JS 版本里用 `createSecureStore()` 做闭包 + Map 存储
- WASM 版本里用 Rust 侧的全局安全存储 `SECURE_STORE`

其共同目标都很明确：

> 不把关键状态直接放在最浅显、最容易被外部直接读写的位置上。

从安全角度看，这当然不是“绝对安全”，但它确实提高了静态分析和脚本直接复用的门槛。

## 八、为什么要做 WASM / JS 双实现

核心实现选择逻辑在 `packages/libs/captcha-core/src/index.ts`。

代码会优先检查环境是否支持 WebAssembly：

```ts
if (checkWasmSupported()) {
  await init();
  return wasmApi as CaptchaCoreAPI;
} else {
  const jsApi = await import('@captcha/core-js');
  return jsApi;
}
```

### 1. 这样设计的直接收益

- **现代浏览器优先使用 WASM，性能和封装性更好**
- **出现加载失败或浏览器不支持时，可以退回 JS 实现，保证可用性**

这是一种很典型的“能力优先 + 兼容兜底”策略。

### 2. 为什么 WASM 不是完全替代 JS，而是与 JS 协作

这里有一个很值得讲的细节：WASM 版本并没有完全自己实现浏览器加密，而是通过 `packages/libs/captcha-core-wasm/src/bridge.js` 去调用 JS 侧封装好的加密能力。

也就是说：

- Rust/WASM 负责更核心的状态管理和流程编排
- JS bridge 负责接浏览器原生的加密接口

这很合理，因为浏览器的 `CryptoKey`、`Web Crypto API` 本来就是 JS 运行时里最自然、最成熟的能力。如果强行在 Rust/WASM 里把所有浏览器加密细节全吃掉，复杂度反而更高。

这在面试里也是加分点：你不是为了“用了 WASM”而用 WASM，而是根据浏览器能力边界做了合理分层。

## 九、第二层兼容：Web Crypto 与 CryptoJS 的降级策略

如果说 `captcha-core` 解决的是“核心实现层面用 WASM 还是 JS”，那么 `packages/libs/utils-crypto` 解决的就是“加密能力层面用原生还是兼容库”。

入口在 `packages/libs/utils-crypto/index.ts`：

```ts
if (isWebCryptoAPISupported) {
  return new WebCryptoManager();
} else {
  const { CryptoJSManager } = await import("./CryptoJSManager");
  return new CryptoJSManager();
}
```

### 1. 为什么这层兼容很重要

就算浏览器支持 JS，也不代表它一定完整支持现代加密 API。所以只做 `WASM -> JS` 的回退还不够，还需要再把“加密库选择”抽象出来。

这意味着项目做的是两层 fallback：

1. **核心实现 fallback**：WASM -> JS
2. **加密能力 fallback**：Web Crypto -> CryptoJS

这套设计明显比“写死一种实现”成熟得多。

### 2. 两种加密实现对外接口保持一致

无论是 `WebCryptoManager` 还是 `CryptoJSManager`，对上层都提供：

- `deriveKey()`
- `encrypt()`
- `decrypt()`

这意味着上层业务代码和 SDK 主链路不用知道底层细节，只依赖统一接口即可。

这是非常标准的抽象方式，也很适合在面试时体现你的“接口设计意识”。

## 十、内部状态保护：为什么它不仅仅是“存个变量”

在很多业务项目里，开发者会把关键状态直接挂在类实例或全局变量上。但这个项目里更进一步做了内部存储封装。

### 1. JS 侧的 `createSecureStore()`

`packages/libs/captcha-utils/src/create-secure-store.ts` 里，用闭包 + `Map` 维护内部存储，并通过编码后的 key 访问数据。

从严格意义上说，这并不能保证绝对安全，但在前端场景里，它确实比“所有值都直接挂在可见对象上”更不容易被脚本直接复用。

### 2. WASM 侧的安全存储

在 `packages/libs/captcha-core-wasm/src/lib.rs` 里，关键状态通过 Rust 侧的全局 `Mutex<HashMap<...>>` 管理，再通过导出函数访问。

这个设计的优势是：

- 核心状态不直接暴露给普通 JS 作用域
- 状态访问路径更集中
- 更适合和 WASM 核心逻辑绑定在一起

## 十一、打包与混淆：为什么一个 SDK 不能只“打出来就行”

从 `packages/libs/captcha-sdk/webpack.config.js` 可以看出，这个项目在工程化上投入不少。

### 1. 当前主构建是 Webpack

README 里还保留了一些 Rollup 的设计痕迹，但从当前仓库代码看，SDK 主包的实际构建核心已经是 Webpack。

这个点值得在技术总结里特别说明：

> 做技术复盘时，要以当前生效的代码实现为准，而不是只看文档描述。

### 2. 有分级混淆策略

配置里对不同目录应用了不同强度的混淆策略：

- 核心逻辑使用更高强度混淆
- 一般业务代码使用中低强度混淆

这说明项目在做一个权衡：

- 既要保护关键逻辑
- 又要避免所有代码都被极端混淆后难以维护和调试

### 3. 做了分包

当前至少把下面这些能力拆成了独立 chunk：

- 指纹库 chunk
- JS 核心实现 chunk
- CryptoJS chunk

这和前面动态导入的设计是配套的：只在需要时加载更重的依赖，避免把所有能力都塞进主包。

### 4. 输出形态偏向“可交付 SDK”

Webpack 输出的是版本化目录下的 UMD 产物，这说明项目的目标不是只给当前站点内部消费，而是考虑了 CDN、脚本接入或跨业务线交付等场景。

## 十二、国际化、错误处理和 Demo：这些“小点”其实很体现产品化意识

### 1. 国际化

`packages/libs/captcha-sdk/src/i18n` 下有 `en`、`zh-CN`、`zh-TW` 等文案，这说明组件不是只面向单一语言环境。

### 2. 错误处理与超时

SDK 里对网络错误、超时错误、初始化失败和验证失败做了不同处理路径，并通过 `onSuccess`、`onFail`、`onError` 向业务暴露。

这类回调拆分对于 SDK 很重要，因为它决定了业务方怎么接入和兜底。

### 3. 示例应用

`packages/apps/captcha-sdk-example` 不是一个可有可无的 demo，而是很重要的“接入验证层”：

- 便于本地调试
- 便于向业务同学演示
- 便于验证 SDK 暴露 API 是否合理

很多 SDK 项目最大的问题就是“能打包，但不好接”。有 demo 的价值就在这里。

## 十三、这个项目最适合怎么讲给前端面试官听

如果面试官是前端方向，我建议不要上来就说“我做了验证码”。更好的说法是：

> 我做的是一个滑块验证码前端 SDK，核心不是 UI，而是把设备指纹、轨迹采集、动态加密和浏览器兼容整合成一条可复用的前端验证链路。

然后再顺着这三层展开：

1. **业务价值**：给业务线提供低成本接入的验证码能力
2. **技术价值**：把设备、行为和会话数据绑定成动态加密链路
3. **工程价值**：做成 monorepo + SDK + 多实现兼容 + 构建发布方案

这样会比单讲“滑块怎么拖动”更有层次。

## 十四、如果让我总结这个项目最值得写进博客的 5 个关键词

- **SDK 化**：不是页面功能，而是可复用能力
- **安全链路**：设备指纹 + 轨迹 + 会话 + 加密
- **双层兼容**：WASM/JS 与 Web Crypto/CryptoJS
- **工程化**：分包、混淆、版本化输出、demo
- **产品化意识**：国际化、回调设计、接入体验

## 十五、还可以继续优化的方向

从当前仓库 README 和实现细节看，这个项目后续还有不少可继续演进的空间：

### 1. 多实例能力

当前 SDK 更偏单例思路。如果未来需要一个页面同时管理多个验证码实例，需要重新设计实例隔离和状态管理。

### 2. 更强的轨迹策略

目前已经有速度与平滑度分析，后续还可以加入更细的异常点检测、轨迹片段特征以及更丰富的服务端联动策略。

### 3. 更完整的测试体系

当前代码里已经能看到对 WASM 的测试入口，但整体上还可以继续加强端到端验证、兼容性验证和核心链路回归测试。

### 4. 接入体验进一步统一

比如更完善的样式定制能力、更清晰的 API 类型导出、更一致的文档和实现同步，这些都能继续提升 SDK 的可维护性。

## 结语

这个项目最有价值的地方，不是它“有一个滑块”，而是它把一个看似简单的交互，真正做成了可交付的前端安全能力。

如果你把它当作一个普通组件来讲，面试价值会打折；但如果你把它当作“前端 SDK + 安全链路 + 兼容性工程”的综合实践来讲，它就会很有代表性。

从当前仓库代码看，这个项目最能体现的，不只是业务功能实现能力，而是：

- 前端抽象能力
- SDK 工程化能力
- 浏览器环境差异处理能力
- 面向安全场景的链路设计能力

这也是为什么它很适合被当作一个重点项目去讲。
