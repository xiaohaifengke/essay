# Monorepo 架构的优势是什么？

## 回答

我一般会先这样回答：

- Monorepo 的核心优势，不只是“把代码放一起”，而是把多个应用和公共能力放到同一个工程体系里统一治理。
- 第一，代码复用更顺。像组件库、hooks、utils、types 这些公共包可以直接共享，跨项目改动成本更低。
- 第二，规范和工具链更统一。比如 eslint、tsconfig、构建脚本、测试规则、CI 流程都能在根目录统一管理。
- 第三，跨项目变更更安全。一个需求如果同时改应用和公共包，可以一次提交完成，避免版本错位。
- 第四，更适合做增量构建和受影响范围分析，配合 Turborepo 或 Nx，CI 效率会明显更好。
- 但我也会补一句，Monorepo 不是天然更优，它更适合有代码共享、统一治理和协同诉求的团队。

## 面试官追问

### 追问 1：Monorepo 最适合什么场景？

我会说，最适合“多个应用 + 多个公共包”这类场景。
比如一个团队同时维护官网、管理后台、移动端，还有自己的组件库、工具库、埋点 SDK，这种时候 Monorepo 的优势会很明显。
如果项目之间几乎没有复用，反而未必值得上 Monorepo。

### 追问 2：Monorepo 的难点是什么？

我会回答，难点其实不在“放到一个仓库”，而在“怎么治理”。
典型问题包括依赖边界容易变乱、仓库变大后构建慢、CI 复杂、以及权限管理不够细。
所以 Monorepo 真正要配套的是任务编排、缓存、依赖约束和目录规范。

### 追问 3：你会怎么描述一个典型的前端 Monorepo 目录结构？

我一般会给面试官一个大概画像，而不是死背具体工具配置。

```text
repo/
├── apps/
│   ├── web/                  # C 端应用 / 官网
│   ├── admin/                # 管理后台
│   └── mobile/               # H5 / 小程序壳
├── packages/
│   ├── ui/                   # 组件库
│   ├── utils/                # 工具函数
│   ├── hooks/                # 通用 hooks
│   ├── types/                # 公共类型
│   └── config/               # 共享工程配置
├── package.json
├── pnpm-workspace.yaml
├── turbo.json                # 或 nx.json
├── tsconfig.base.json
├── .eslintrc.cjs
├── .prettierrc
├── .changeset/               # 如果要管理包版本
└── .github/workflows/
```

我会补一句：`apps` 放可运行应用，`packages` 放可复用能力，这样职责更清晰，后面做依赖分析和按需构建也更方便。

### 追问 4：这些配置文件里，哪些最关键？

我一般会抓 5 个最重要的讲：

- `pnpm-workspace.yaml`：定义哪些目录属于 workspace，没有它就没有真正的 Monorepo 包关系。
- 根目录 `package.json`：统一脚本入口，比如 `dev`、`build`、`lint`、`test`。
- `turbo.json` 或 `nx.json`：决定任务编排、缓存和受影响项目构建，是工程提效的关键。
- `tsconfig.base.json`：统一 TypeScript 配置和路径别名，保证类型和 import 规则一致。
- ESLint / Prettier / CI 配置：保证多人协作时规范一致，不然仓库放一起也会很乱。

### 追问 5：为什么很多团队会单独放一个 `config` 包？

因为工程配置本身也是可以复用的。
比如 eslint config、tsconfig、tailwind preset、babel config，都可以做成共享包。
这样每个项目只继承，不需要复制粘贴，长期维护成本会低很多。

### 追问 6：Monorepo 和 Multirepo 怎么选？

我会说，看项目之间是不是“强协同”。
如果多个项目共享代码很多、需要统一规范、还经常一起改，那 Monorepo 更合适。
如果项目完全独立、发布节奏不同、权限边界要求又很强，那 Multirepo 可能更自然。

## 可举的项目例子

如果面试官让我结合项目讲，我会这样组织：

- 我们有多个前端应用，比如官网、后台和活动页，同时还有公共组件库和工具库。
- 以前分仓库维护时，公共组件升级经常要多个项目分别发版和升级，沟通成本很高。
- 后来做成 Monorepo 后，组件、类型、eslint 配置、构建脚本都统一了，一个需求可以在同一次提交里改完。
- 真正收益不是“目录更好看”，而是公共能力复用更自然，CI 也能按受影响范围执行，整体效率更稳定。

## 易踩坑

- 不要只说“代码放一起更方便”，这太浅了，要讲统一治理和跨项目协同。
- 不要把 Monorepo 说成万能方案，面试官通常会追问成本和边界。
- 不要只背工具名，比如 Nx、Turborepo、pnpm，要讲它们分别解决什么问题。
- 讲目录结构时，不要陷入细节配置背诵，重点是职责划分和工程收益。
- 如果说到了增量构建，最好补一句“受影响范围分析 + 缓存 + 任务编排”。
