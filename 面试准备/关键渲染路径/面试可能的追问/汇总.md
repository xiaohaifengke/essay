# 关键渲染路径 - 面试追问汇总

---

## 第一维度：性能优化实战 (The "So What?" Layer)

**核心目的**：考察你是否能将理论转化为性能优化的手段。

### 追问 1：强制同步布局与布局抖动

> 你刚才提到了回流（Reflow）成本很高，那在实际开发中，什么代码会导致"强制同步布局" (Forced Synchronous Layout) 或"布局抖动" (Layout Thrashing)？该如何避免？

**考察点**：

- 是否知道在 JS 循环中**交替读取几何属性**（如 `offsetWidth`）和**写入样式**会导致浏览器被迫频繁计算布局。
- 是否了解**读写分离（Read-Write Batching）** 或 FastDOM 等库。

**参考回答**：

> **原因**：当代码在修改了样式（Write）后紧接着读取几何属性（Read，如 `offsetTop`, `getComputedStyle` 等），浏览器为了返回最新准确的值，必须强制提前执行布局计算，这叫**强制同步布局**。如果在循环中这样做，就会导致浏览器在每一帧内反复进行多次布局计算，产生**布局抖动**。
>
> **避免方案**：
>
> 1. **读写分离**：先进行所有的读取操作，统一保存后再进行所有的写入操作。
> 2. **异步批处理**：使用 `requestAnimationFrame` 将写入操作推迟到下一帧绘制前统一处理。
> 3. **使用工具库**：如 FastDOM，它通过内部队列自动管理读写任务的调度。

### 追问 2：CSS 动画为什么推荐 transform 和 opacity

> 为什么 CSS 动画推荐使用 `transform` 和 `opacity`，而不是 `left`/`top` 或 `background-color`？从渲染流水线的角度解释一下。

**考察点**：

- 是否真正理解"合成（Composite）"步骤。
- 能否答出 `transform` 会开启**硬件加速（GPU）**，直接跳过 Layout 和 Paint 阶段，只在 Composite 阶段处理。

**参考回答**：

> **核心理由**：`transform` 和 `opacity` 的更改可以避开渲染流水线中开销最大的 **Layout (布局)** 和 **Paint (绘制)** 阶段。
>
> 1. **跳过流水线**：这两类属性的改变可以直接在 **Composite (合成)** 阶段由 GPU 处理。由于不涉及几何形状的改变，浏览器不需要重新计算所有元素的坐标，也不需要重绘像素。
> 2. **图层提升 (Layer Promotion)**：它们通常会触发浏览器创建独立的合成层（Composited Layer）。在动画过程中，GPU 只需要移动这个图层或改变其透明度，而不影响主线程上的其他渲染工作，极大地提高了动画的流畅度（60fps）。

### 追问 3：requestAnimationFrame 的执行时机

> `requestAnimationFrame` (rAF) 在渲染流程的哪一步执行？为什么用它做动画比 `setTimeout` 好？

**考察点**：

- 是否理解浏览器刷新频率（60Hz）与 JS 执行时机的关系。
- rAF 保证在每一帧的 Layout **之前**执行，避免丢帧。

**参考回答**：

> **执行时机**：rAF 的回调是在浏览器**下一次重绘（Repaint）之前**执行的，处于渲染流水线的起始阶段（在样式计算和布局之前）。
>
> **优势**：
>
> 1. **同步刷新率**：rAF 自动跟随屏幕的刷新频率（通常 60Hz），确保动画更新与显示器的垂直同步信号（VSync）对齐。
> 2. **节省功耗**：当页面标签处于后台或隐藏状态时，rAF 会自动停止执行，而 `setTimeout` 会继续工作。
> 3. **批处理**：浏览器能保证每帧只执行一次 rAF 回调，避免了 `setTimeout` 因执行时机不确定（作为宏任务）导致的在一帧内执行两次或跳过某一帧（丢帧）的现象。

## 第二维度：资源加载与阻塞 (The Blocking Layer)

**核心目的**：考察对关键渲染路径（CRP）的控制能力。

### 追问 4：defer 和 async 的区别

> `<script>` 标签放在 `<head>` 里，加上 `defer` 和 `async` 属性，在渲染流程上有什么具体区别？

**考察点**：
| 类型 | 行为 |
| :--- | :--- |
| **普通 script** | 暂停 DOM 构建，下载并执行。 |
| **async** | 异步下载，下载完**立即执行**（可能暂停 DOM 构建），执行顺序不固定。 |
| **defer** | 异步下载，等到 DOM 构建完成（`DOMContentLoaded` 前）**按顺序执行**。 |

**参考回答**：

> 1. **async (异步)**：脚本的下载不会阻塞 DOM 解析。但**一旦下载完成，脚本会立即执行**，这时如果 DOM 还没解析完，解析会暂停。多个 async 脚本谁先下载完谁先执行，顺序不可控。适合不依赖 DOM 且相互独立的脚本（如埋点、统计）。
> 2. **defer (延迟)**：脚本下载也不会阻塞 DOM 解析。不同的是，脚本会等到 **DOM 全部解析完毕**、在 `DOMContentLoaded` 事件触发前才按顺序执行。它保证了脚本执行时 DOM 节点已就绪，且脚本顺序与声明顺序一致。

### 追问 5：CSS 加载慢会怎样

> 如果 CSS 文件很大，下载很慢，页面会显示什么？是白屏还是无样式的 HTML 内容？

**考察点**：

- 考察对 **CSSOM 阻塞渲染**特性的理解。
- 通常浏览器会**等待 CSSOM 构建完成**才渲染 Render Tree（白屏），以避免 FOUC（无样式内容闪烁），但不同浏览器策略略有不同。

**参考回答**：

> **现象**：大部分浏览器默认会表现为**白屏**（渲染被阻塞）。
>
> **原因**：虽然 CSS 不阻塞 DOM 的解析，但它**严格阻塞渲染**。浏览器在没有拿到完整的 CSSOM 之前，无法构建出正确的渲染树（Render Tree）。如果允许在没有样式的情况下渲染，用户会先看到一闪而过的、混乱的纯 HTML（即 **FOUC** 问题），随后样式加载后再跳动。为了用户体验，浏览器选择等待 CSS 下载并解析完毕再进行首次渲染。
>
> **优化建议**：使用内联关键 CSS、减少 CSS 文件体积或利用媒体查询拆分非关键 CSS。

## 第三维度：结合现代框架 (The Framework Layer)

**核心目的**：结合你擅长的 React/Next.js/Vue，考察原理与框架的联系。

### 追问 6：Virtual DOM 的核心价值

> React/Vue 的 Virtual DOM (虚拟 DOM) 的核心价值，在渲染原理的哪个环节体现得最明显？

**考察点**：

- **不要只回答"快"**。
- 核心价值是 **Batching（批处理）**。VDOM 在内存中进行 Diff，计算出最小变更集，然后**一次性更新真实 DOM**，从而将多次可能的 Layout/Paint 合并为一次，减少渲染流水线的调用次数。

**参考回答**：

> VDOM 的核心价值在于**将多次 DOM 操作合并为一次高性能的更新**，主要体现在渲染流水线的 **Batching (批处理)** 上。
>
> 1. **最小化 Reflow/Repaint**：在没有 VDOM 的情况下，频繁地手动更新 DOM（如循环插入 `<li>`）会导致浏览器反复触发渲染流水线。
> 2. **异步更新策略**：VDOM 允许框架在内存中构建一棵完整的变更树（Diff 过程），算出最终的差异。然后在下一个 tick 中，一次性将这些变更应用到真实 DOM 上。这确保了在一次渲染循环周期内只触发一次 Layout 和 Paint，极大地保护了浏览器的性能。

### 追问 7：SSR 水合期间发生了什么

> 在 Next.js (SSR) 场景下，HTML 是服务端直出的，那为什么页面在"水合 (Hydration)" 之前无法交互？这期间渲染流水线发生了什么？

**考察点**：

- SSR 只是**加快了首屏的 Layout 和 Paint**（用户看得到），但 JS 还没下载执行（Event Listeners 没绑定）。
- 考察对 **Time to Interactive (TTI)** 和 **First Contentful Paint (FCP)** 差异的理解。

**参考回答**：

> **原因**：服务端直出的 HTML 只包含了静态的结构和样式，但在此时页面并未携带 **JavaScript 逻辑和事件监听器**。
>
> **流水线过程**：
>
> 1. 用户看到的是首屏渲染（FCP）的结果，浏览器已经完成了 HTML 解析、CSSOM 构建和初步的 Paint。
> 2. 与此同时，浏览器正在下载该页面的 JS Bundle。
> 3. 下载并执行 JS 后，React/Vue 开始执行**水合阶段**：在内存中构建 VDOM，并将其与现有的真实 DOM 节点进行对比、绑定事件（Event Listeners）。
> 4. **总结**：在水合完成之前，DOM 元素虽然存在，但负责处理交互（如点击、输入）的 JS 逻辑还没“活”过来，所以无法交互。这种情况通常被称为“**TTI（可交互时间）晚于 FCP**”。

## 第四维度：细节与坑 (The Detail Layer)

**核心目的**：考察基本功的细腻程度。

### 追问 8：display: none vs visibility: hidden vs opacity: 0

> 从渲染流水线的角度看，`display: none`、`visibility: hidden` 和 `opacity: 0` 有什么本质区别？

**参考回答**：

> 1. **`display: none`**：元素会从渲染树（Render Tree）中被**彻底移除**。因为它不再占据空间，所以它的显示/隐藏会触发 **Reflow (回流)** 和 **Repaint (重绘)**。
> 2. **`visibility: hidden`**：元素**保留在渲染树中**并在屏幕上占据空间（占位），只是不可见。它的改变不会影响几何布局，因此只会触发 **Repaint (重绘)**。
> 3. **`opacity: 0`**：元素同样**在渲染树中**且占据空间。如果配合 `will-change: opacity` 触发了图层提升，它的改变可以在 GPU 层面完成，从而**仅触发 Composite (合成)**，甚至跳过重绘，这是性能最优的隐藏方式。
