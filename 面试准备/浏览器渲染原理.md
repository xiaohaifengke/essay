# 浏览器渲染原理

## 回答

我一般会先这样回答：

- 浏览器渲染，本质上就是把 HTML、CSS、JavaScript 最终变成屏幕上的像素。
- 整体流程可以概括成 6 步：解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，合成 Render Tree，做 Layout，接着 Paint，最后 Composite。
- 其中性能最敏感的通常是布局和绘制，因为这两步最容易带来卡顿、白屏时间变长，或者页面抖动。
- JavaScript 和 CSS 都可能影响渲染节奏。脚本默认会阻塞解析，CSS 会阻塞渲染，而且还会间接影响后续脚本执行。
- 从前端优化角度看，核心就是尽量减少阻塞资源、减少回流重绘、把动画优先放到 `transform` 和 `opacity` 这类更适合合成阶段的属性上。
- 如果面试官继续追问，我一般会再展开讲关键渲染路径、回流重绘、以及首屏优化。

## 面试官追问

### 追问 1：浏览器渲染的完整流程你会怎么展开讲？

我会按顺序讲：先解析 HTML 生成 DOM，再解析 CSS 生成 CSSOM，然后把两者合成 Render Tree。
接下来浏览器会做 Layout，算出每个元素的位置和尺寸；然后做 Paint，把颜色、文字、边框这些真正画出来；最后再做 Composite，把不同图层合成到屏幕上。
如果只记一句话，我会记成：`DOM -> CSSOM -> Render Tree -> Layout -> Paint -> Composite`。

### 追问 2：CSS 和 JavaScript 分别是怎么影响渲染的？

我会说，JavaScript 默认会阻塞 HTML 解析，因为浏览器要先执行脚本，避免脚本修改 DOM 后前面白解析了。
CSS 一般不会阻塞 HTML 解析，但会阻塞渲染，因为浏览器得先知道元素最终长什么样，才能避免页面先裸奔再闪一下样式。
另外 CSS 还会间接影响脚本执行，因为脚本可能读取样式结果，所以浏览器通常会等 CSSOM 就绪。

### 追问 3：回流、重绘、合成有什么区别？

这是性能题里很高频的追问。
回流是重新计算布局，代价最大；重绘是不改布局，只重画外观；合成是直接在图层层面做处理，成本通常最低。
所以像改 `width`、`margin` 这类属性，往往比改 `color` 更重；而改 `transform`、`opacity` 一般只走合成，性能会更稳定。

### 追问 4：为什么动画一般推荐用 `transform` 和 `opacity`？

因为这两个属性通常不会触发布局，很多时候也不需要重新绘制，主要走合成阶段。
这样浏览器更容易把动画交给合成线程或 GPU 处理，掉帧概率会低很多。
所以做位移、缩放、淡入淡出时，我优先考虑它们，而不是直接改 `top`、`left`。

### 追问 5：从工程角度，你会怎么优化浏览器渲染性能？

我通常会从三层看：第一是减少阻塞，比如脚本用 `defer`、资源拆分、首屏 CSS 优先；第二是减少无意义的回流重绘，比如批量改 DOM、避免频繁读写交替；第三是让更新更“轻”，比如动画走 `transform`，长列表做虚拟化。
如果是首屏问题，我还会结合关键渲染路径去看资源加载顺序和体积。

### 追问 6：关键渲染路径和浏览器渲染原理是什么关系？

我会说，浏览器渲染原理讲的是“页面怎么被画出来”，关键渲染路径讲的是“首屏这条链路里，哪些步骤和资源决定了页面什么时候能显示出来”。
所以关键渲染路径更偏性能视角，是渲染原理在首屏优化场景下的一种落地分析方式。

## 可举的项目例子

如果面试官让我结合项目讲，我一般会这么说：

- 我们做过一个数据量比较大的后台页面，首屏慢和滚动卡顿都比较明显。
- 后来排查发现，一部分问题是首屏阶段脚本和样式资源太重，另一部分问题是列表区域频繁读写 DOM，导致回流比较多。
- 优化时我们做了几件事：首屏脚本延后、关键样式前置、列表区域减少同步布局读取、动画统一改成 `transform`。
- 最后的经验是，性能问题不能只看接口慢不慢，很多时候是浏览器渲染链路本身被阻塞了。

## 易踩坑

- 不要只背“DOM、CSSOM、Render Tree”这几个词，面试官更想听你知不知道它们和性能的关系。
- 不要把“CSS 不阻塞解析”简化成“CSS 不影响渲染”，这两个不是一回事。
- 不要把回流和重绘混为一谈，面试里很容易被继续追问。
- 讲动画优化时，不要只说“用 GPU 加速”，最好补一句为什么 `transform`、`opacity` 更稳。
- 如果讲首屏优化，尽量顺手带一下关键渲染路径、阻塞资源和资源加载顺序。
