# 开发一个 CLI 工具需要了解哪些知识点？

## 回答

我一般会先这样回答：

- 如果让我从零写一个 CLI 工具，我会先从 7 个方面看：命令设计、输入输出、系统能力、调试联调、错误处理、工程化、发布分发。
- 第一层是交互协议，也就是命令、子命令、参数、flag、帮助信息、退出码怎么设计，因为 CLI 本质上也是一种“接口”，只是它的消费者是人和脚本。
- 第二层是底层能力，比如文件系统、路径处理、环境变量、进程管理、网络请求、标准输入输出，这些决定这个工具到底能做什么。
- 第三层是调试和联调能力，尤其是 Node.js CLI 常见的 `bin` 字段、shebang、`npm link` / `pnpm link`、PATH、以及如何像真实全局命令一样去验证入口有没有挂对。
- 第四层才是用户体验，比如提示信息是否清晰、命令是否幂等、是否支持 `--help`、`--version`、`--dry-run`、非交互模式和批处理模式。
- 第五层是工程质量，比如日志、配置、测试、跨平台兼容、性能、可观测性、异常处理，不然工具很容易变成“本机能跑、别人一用就坏”。
- 第六层是发布和维护，比如怎么安装、怎么升级、怎么兼容旧参数、怎么做文档和示例，这部分往往比“把功能写出来”更像真实工程。
- 另外我会把 CLI 调试分成两类：一类是入口联调，确认命令有没有被正确安装和执行；另一类是运行期排障，确认命令执行后为什么出错。
- 所以面试里我会总结成一句话：**CLI 工具不是简单脚本，它本质上是一个面向终端用户和自动化流程的产品化接口。**

## 面试官追问

### 追问 1：CLI 工具和普通脚本有什么区别？

普通脚本往往是“我自己临时跑一下就行”，但 CLI 工具要面向别人反复使用。
所以它更强调稳定的命令协议、明确的输入输出、可预期的退出码、清晰的帮助文档，以及可安装、可升级、可维护。

### 追问 2：如果让你设计一个 CLI，第一步会做什么？

我不会一上来就写代码，而是先定义命令模型。
比如主命令是什么、有没有子命令、参数是位置参数还是 flag、哪些是必填、哪些支持默认值、错误输入时给什么提示。
因为这一步本质上是在定义这个工具的“对外 API”。

### 追问 3：写 CLI 工具时要重点掌握哪些底层知识？

我会优先掌握 5 类：`argv` 参数解析、`stdin/stdout/stderr`、文件系统和路径、环境变量、子进程管理。
因为大多数 CLI 不是在读文件，就是在写文件、调命令、读配置、吐结果，这几类能力基本是核心地基。

### 追问 4：CLI 工具为什么要关注退出码和非交互模式？

因为 CLI 往往不只是给人手敲，还会被 CI、脚本、定时任务调用。
如果退出码不规范，自动化流程就没法准确判断成功失败；如果只能交互确认，放进流水线里就会卡住。
所以一个成熟 CLI 一般都会区分成功、业务失败、参数错误这些状态，并支持非交互执行。

### 追问 5：一个真正可用的 CLI 工具，工程上还要补哪些东西？

至少要补齐帮助文档、示例、日志、配置加载、测试、跨平台兼容、安装方式和版本管理。
如果再往上走，可能还要考虑插件化、权限控制、并发处理、输出格式标准化，比如支持 `json` 输出，方便别的系统接它。

### 追问 6：如果用 Node.js 写 CLI，还会补充哪些知识点？

我会补充 `process.argv`、`process.env`、`fs`、`path`、`child_process`、`stream`、shebang、`package.json` 里的 `bin` 字段，以及 `npm`/`pnpm` 下的分发方式。
另外还要注意 ESM/CJS、Windows 和 Unix 路径差异、换行符差异，以及命令在不同 shell 下的兼容性。

### 追问 7：Node.js CLI 开发时为什么经常会用到 `npm link`？

因为开发 CLI 时，最常见的需求不是“把函数跑起来”，而是“像真实全局命令一样去跑它”。
`npm link` 或 `pnpm link` 可以把本地包临时挂到全局环境里，方便你直接在终端输入命令名联调，看 `bin` 字段、shebang、入口文件、依赖解析是不是都正确。
所以它更像是 CLI 开发阶段的本地安装和联调手段，而不只是一个普通的包管理命令。

## 可举的项目例子

如果面试官让我结合项目讲，我一般会这么说：

- 我做这类工具时，最开始以为核心难点是把功能实现出来，后来发现真正费时间的是参数设计、错误提示、日志和跨平台兼容。
- 比如一个批处理 CLI，开发阶段我会先用 `npm link` 去模拟全局命令调用，先确认 `bin` 挂载、入口路径和执行方式都没问题；等命令本身能稳定跑起来之后，再看 `--dry-run`、退出码、错误日志这些运行期排障能力。
- 后来我们会把 CLI 当成一个正式接口来设计：命令协议先定清楚，输出结构可预期，交互模式和非交互模式分开，配置优先级也明确。
- 这个过程让我意识到，CLI 的本质不是“能跑”，而是“能长期稳定地被人和系统使用”。

## 易踩坑

- 不要只盯着参数解析库，真正难的是命令设计、错误处理和可维护性。
- 不要把 CLI 写成只能人工点确认的交互脚本，很多场景它需要接入自动化流程。
- 不要把“CLI 调试”只理解成打日志，开发期还要会用 `bin`、shebang、`npm link` / `pnpm link` 去联调命令入口。
- 不要忽略退出码、`stderr` 和日志分层，不然出了问题很难排查。
- 不要默认所有环境都和本机一样，路径、权限、shell、编码、换行符都可能有差异。
- 不要一开始就把工具和业务逻辑强耦合，后期一旦要扩命令或做插件化会很痛苦。
