# React 相关高频考点

## 回答

我一般会先这样回答：

- 如果面试官问 React 高频考点，我不会只背 Hooks，而是会从组件化思想、数据流、渲染机制、状态管理、性能优化、工程实践这几条主线去讲。
- 第一组高频点是 `props`、`state`、单向数据流，因为这是 React 最基础的心智模型：数据往下流，交互往上抛，视图由状态驱动。
- 第二组是组件更新机制，比如 `setState` / `useState`、批量更新、重新渲染、`key`、Diff、Fiber，这部分很容易被继续追问到“为什么 React 能高效更新”。
- 如果要顺手解释 Fiber，我会说它可以理解成 React 16 之后底层的一套协调架构，它把更新过程拆得更细，让 React 能按优先级调度更新，而不是一口气把整棵组件树同步跑完。
- 第三组是 Hooks，尤其是 `useEffect`、`useMemo`、`useCallback`、`useRef`，面试官一般不只问会不会用，而是会追问依赖项、闭包问题、副作用时机和性能取舍。
- 第四组是生命周期和副作用管理。虽然函数组件已经是主流，但很多问题本质上还是“什么时候挂载、更新、卸载，副作用应该放在哪”。
- 第五组是性能优化，比如状态粒度拆分、减少无效渲染、列表 `key`、`memo`、懒加载、长列表优化，这类题通常会和真实项目结合着问。
- 第六组是工程化相关，比如受控组件、表单处理、状态提升、Context、路由、SSR/Hydration，这些在中高级前端面试里也很常见。
- 所以我通常会总结成一句话：**React 高频考点不是 API 清单，而是“状态怎么驱动 UI、UI 为什么会更新、更新怎么更稳更快”这三件事。**

## 面试官追问

### 追问 1：React 为什么强调单向数据流？

因为单向数据流更容易定位数据变化来源，组件之间的依赖关系也更清晰。
当页面复杂度上来后，如果数据能随意双向改动，状态会很难追踪，排查问题成本会明显上升。

### 追问 2：`state` 和 `props` 的区别是什么？

`props` 是外部传入的，只读，主要用来做父子组件通信；`state` 是组件内部维护的，会随着交互和业务逻辑变化。
可以简单理解成：`props` 决定你“拿到什么数据”，`state` 决定你“当前是什么状态”。

### 追问 3：React 为什么需要 `key`？

`key` 的核心作用不是消除警告，而是帮助 React 在同层级节点比较时稳定识别元素身份。
如果 `key` 不稳定，比如直接用索引，在列表插入、删除、重排时就可能导致节点复用错误，出现状态错乱和不必要的重新渲染。

### 追问 4：`useEffect` 为什么这么容易出问题？

因为它本质上是在处理副作用，而副作用天然就和时机、依赖、闭包绑定在一起。
很多问题不是 API 本身复杂，而是开发者没想清楚“这个 effect 依赖谁、什么时候应该重新执行、清理逻辑该放哪”。

### 追问 5：React 的渲染和提交大概是怎么回事？

可以粗略理解成两步：先计算这次更新后 UI 应该长什么样，再把最终变更提交到真实 DOM。
前面更偏协调和比较，后面更偏真正落到界面，所以 React 的高效更新不是“每次都重画整个页面”，而是先算差异，再批量提交。
如果结合 Fiber 来说，Fiber 主要提升的是前面的协调和调度能力：渲染阶段可以拆分、暂停、恢复，但提交阶段通常还是要尽快一次性完成。

### 追问 6：Fiber 到底解决了什么问题？

我不会把它简单说成“Fiber 让 React 更快”，更准确的说法是：它让 React 的更新更可控。
早期 React 更新更偏同步递归，一旦组件树很大，主线程就可能被长时间占住，用户输入、动画、点击反馈都会受影响。
Fiber 把每个组件节点都变成更细的工作单元之后，React 就更容易做任务切片、优先级调度、暂停和恢复，所以复杂页面下的交互体验会更稳。

### 追问 7：Fiber 和浏览器 Event Loop、`requestIdleCallback` 是什么关系？

我会先把这三个概念拆开。
Event Loop 是浏览器主线程调度任务和渲染时机的机制；Fiber 是 React 内部的协调架构；`requestIdleCallback` 更像浏览器提供的一个“空闲时再执行低优先级任务”的调度点。
它们的关系是：Fiber 让 React 有能力把渲染阶段拆成更细的任务块，然后调度器再找合适的时机去执行这些任务，这样 React 就不至于长时间霸占主线程。
但面试里不要把它简化成“Fiber 就是基于 `requestIdleCallback` 实现的”，更准确的说法是：`requestIdleCallback` 能帮助理解“利用空闲时间做低优先级工作”这个思路，但 Fiber 本质上是 React 的架构升级，不等于某一个浏览器 API。

### 追问 8：React 里常见的性能优化手段有哪些？

我一般会先从减少无意义渲染入手，比如合理拆组件、稳定 `key`、用 `memo`、`useMemo`、`useCallback` 控制引用变化。
如果场景再大一点，就会考虑懒加载、代码分割、长列表虚拟化，以及避免把大而全的状态放在过高层级。

### 追问 9：Hooks 是不是比 class component 更高级？

我不会直接说“更高级”，而是说它更符合现在 React 的主流组织方式。
Hooks 的优势是复用逻辑更自然、状态和副作用更容易按功能聚合，但底层问题并没有消失，比如闭包、渲染时机、依赖管理还是得理解清楚。

### 追问 10：`memo`、`useMemo` 和 `useCallback` 的作用和区别是什么？

这三个 API 都是 React 中用于**性能优化的缓存手段**，但它们作用的细粒度不同：

1. **`React.memo`（组件级缓存）**：
   - **作用**：是一个高阶组件，用于缓存整个父组件重新渲染时当前组件的渲染结果。
   - **机制**：默认会对传入的 `props` 进行浅比较。如果父组件重新渲染，但传给该组件的 `props` 未变，被 `memo` 包装的子组件就会跳过本次渲染。
   - **场景**：适用于渲染开销较大的纯组件，防止无意义的重新渲染。

2. **`useMemo`（数据/计算级缓存）**：
   - **作用**：用于缓存复杂的计算结果或引用类型的数据（例如对象、数组）。
   - **机制**：接收一个函数和依赖数组，只有依赖项改变时才重新计算并返回新值，否则复用上一次的值。
   - **场景**：避免每次渲染时都进行昂贵的计算；或者保持引用地址不变，以便配合传递给被 `React.memo` 包裹的子组件。

3. **`useCallback`（函数级缓存）**：
   - **作用**：专门用于缓存函数的引用地址（它本质上是 `useMemo` 用来返回函数的语法糖）。
   - **机制**：接收一个回调函数和依赖数组，依赖不变时返回同一个函数引用。
   - **场景**：当组件向子组件传递回调函数时，如果子组件使用了 `React.memo`，用 `useCallback` 包裹回调可以防止因为父组件渲染导致函数引用更新，从而破坏子组件的缓存机制。

**一句话总结**：`memo` 管“组件不乱更新”，`useMemo` 管“数据不乱算/引用不改变”，`useCallback` 管“函数引用不乱变”。后两个往往是为了配合第一个起作用的。

## 可举的项目例子

如果面试官让我结合项目讲，我一般会这么说：

- 我在 React 项目里最深的感受是，很多问题表面看像“页面卡”或者“状态乱”，本质上其实是组件边界、状态粒度和副作用管理没设计好。
- 比如一个复杂列表页，如果把筛选条件、分页、弹窗状态、表单状态全堆在最外层，稍微一改就会带着整棵子树一起重新渲染，后面维护也会很痛苦。
- 后来我们会把状态按业务责任拆开，把公共逻辑抽成自定义 Hook，把高频变化和低频变化分层，再配合 `memo`、稳定 `key` 和长列表优化，整体体验会明显好很多。
- 所以 React 在工程里真正考验的，不只是会不会写 JSX，而是你能不能把“组件、状态、副作用、渲染成本”一起设计清楚。

## 易踩坑

- 不要把 React 面试答成 Hooks API 清单，面试官更关心你有没有完整的渲染和状态心智模型。
- 不要把 `key` 只理解成“为了消除 warning”，它本质上影响节点复用和更新正确性。
- 不要把 `useEffect` 当成“什么逻辑都能往里塞”的地方，很多计算逻辑其实不应该写成副作用。
- 不要一提性能优化就只背 `useMemo`、`useCallback`，先问自己有没有真的出现无效渲染和引用抖动。
- 不要把 Fiber 说成“新的 Diff 算法”或者“React 变快的万能答案”，重点应该是：它让渲染阶段更可切分、可中断、可按优先级调度。
- 不要把 Fiber 直接等同于 `requestIdleCallback`，一个是 React 的协调架构，一个只是浏览器提供的调度时机。
