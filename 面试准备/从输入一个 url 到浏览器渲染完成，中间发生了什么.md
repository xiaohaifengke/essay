# 从输入一个 URL 到浏览器渲染完成，中间发生了什么？

## 回答

我一般会把这个问题拆成两大阶段：**网络阶段** 和 **渲染阶段**。

- 第一，浏览器会先解析 URL，判断协议、域名、端口这些信息，并检查缓存、DNS、连接是否可复用。
- 第二，如果本地没有直接命中可用结果，就会发起网络请求。这里通常会经历 DNS 解析、TCP 或 QUIC 连接、TLS 握手，然后服务器返回 HTML。
- 第三，浏览器拿到 HTML 之后不会等全部下载完才开始，而是边下载边解析，构建 DOM。
- 第四，解析过程中如果遇到 CSS，会去构建 CSSOM；如果遇到 JavaScript，脚本默认可能阻塞解析和后续渲染。
- 第五，DOM 和 CSSOM 合成 Render Tree，再经过 Layout、Paint、Composite，页面才真正显示到屏幕上。
- 所以这道题本质上考两件事：前半段是“资源怎么拿到”，后半段是“内容怎么画出来”。

## 面试官追问

### 追问 1：输入 URL 后，浏览器第一步到底在做什么？

我会先回答“先做导航准备”。
浏览器会解析这个 URL，确认是 `http` 还是 `https`，目标域名是什么，是否有缓存、是否需要走 Service Worker、是否已有可复用连接。
这些都处理完，才会真正进入网络请求阶段。

### 追问 2：网络请求阶段通常会经历哪些步骤？

我一般会说，经典流程是：DNS 解析域名拿到 IP，接着建立 TCP 连接，如果是 HTTPS 还要做 TLS 握手，然后浏览器发送 HTTP 请求，服务器返回响应。
如果是 HTTP/2，会在一个连接里复用多个请求；如果是 HTTP/3，底层则是 QUIC，不再是传统 TCP。
面试里不一定要把协议细节全展开，但最好知道这条链路为什么会影响首屏时间。

### 追问 3：浏览器拿到 HTML 后，为什么页面不是立刻就显示？

因为 HTML 只是原始文本，浏览器还得把它解析成 DOM，再结合 CSS 解析出来的 CSSOM，生成 Render Tree。
之后还要做 Layout 去计算位置和大小，再 Paint 和 Composite。
也就是说，拿到响应只是开始，不等于已经渲染完成。

### 追问 4：CSS 和 JavaScript 在这个过程中分别会带来什么影响？

CSS 主要影响渲染，因为浏览器要先知道元素最终样式，才能稳定地画页面。
JavaScript 默认会阻塞 HTML 解析，因为它可能改 DOM；而且脚本也可能依赖样式结果，所以 CSS 还会间接影响脚本执行时机。
这也是为什么首屏优化经常会谈脚本延后和关键 CSS 前置。

### 追问 5：从“看到页面”这个角度，哪些时间点比较关键？

我会提几个常见节点：`DOMContentLoaded` 代表 HTML 解析完成，`load` 代表页面资源基本加载完成。
但真正的“用户感觉页面出来了”，更接近 `FCP` 或 `LCP` 这类指标。
所以做性能优化时，不能只看接口返回时间，还要看浏览器什么时候真正把内容画出来。

### 追问 6：如果面试官继续问优化，你会怎么答？

我会从两段来讲。
网络阶段重点是减少请求耗时，比如 DNS 预解析、连接复用、CDN、压缩、缓存；渲染阶段重点是减少阻塞和重计算，比如脚本用 `defer`、关键 CSS 前置、减少回流重绘。
这样回答会比较完整，也能自然过渡到性能优化题。

## 可举的项目例子

如果面试官让我结合项目讲，我一般会这么说：

- 我们排查过一个首屏慢的问题，接口本身不算特别慢，但页面还是很久才能稳定显示。
- 后来拆开看，发现前半段是静态资源请求链路比较长，后半段是首屏脚本和样式阻塞了渲染。
- 优化时一部分做在网络层，比如缓存和资源压缩；另一部分做在前端层，比如关键 CSS 前置、非关键脚本延后、减少首屏同步执行逻辑。
- 这个问题最典型的点就在于：从输入 URL 到页面真正可见，中间不是一个点，而是一整条链路。

## 易踩坑

- 不要把这个题只答成“DNS -> TCP -> HTTP 返回”，后半段渲染流程也一定要讲。
- 也不要只答“DOM -> CSSOM -> Render Tree”，前半段网络导航同样是重点。
- 不要把 `DOMContentLoaded` 和“页面完全可见”画等号，这两个概念不一样。
- 讲优化时，不要只说“减少请求数”，还要结合阻塞资源和渲染链路。
- 如果提到 HTTPS、HTTP/2、HTTP/3，不需要背协议细节，但最好知道它们为什么会影响性能。
