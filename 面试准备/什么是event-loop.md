# 什么是 Event Loop？

## 回答

我一般会先这样回答：

- Event Loop 本质上是浏览器或运行时用来协调“同步代码、异步回调、微任务、渲染时机”的一套调度机制。
- 因为 JavaScript 主线程通常是单线程的，一次只能做一件事，所以异步任务不能直接插队执行，而是先进入对应队列，等调用栈清空后再由 Event Loop 调度。
- 在浏览器里，可以粗略理解成：执行一个宏任务，清空当前轮次的微任务，然后浏览器拿到一次渲染机会，最后再进入下一轮任务。
- 这个“渲染机会”很重要，因为 DOM 改了不等于立刻上屏；很多框架也会利用这一点，把同一轮里的多次状态变化先合并，再统一提交 DOM 更新。
- 所以 Event Loop 解决的核心问题，不只是“让单线程 JS 能有序处理异步任务”，还包括“决定浏览器什么时候有机会把这轮改动真正画到屏幕上”。
- 面试里如果再往下问，一般就会追问宏任务、微任务、Promise、setTimeout、渲染时机，以及框架为什么能批量更新。

## 面试官追问

### 追问 1：你说的调用栈、任务队列、微任务队列分别是什么？

我会说，调用栈就是当前正在执行的同步代码。
异步任务不会直接进调用栈，而是等时机成熟后进入队列。
其中常见会分成宏任务队列和微任务队列，Event Loop 会按固定顺序把它们调度回主线程执行。

### 追问 2：宏任务和微任务有什么区别？

我一般会回答，宏任务可以理解成“一个大的执行单元”，比如 `setTimeout`、`setInterval`、I/O、UI 事件。
微任务优先级更高，通常会在当前宏任务结束后、进入下一轮事件循环前立即清空，比如 `Promise.then`、`MutationObserver`。
所以面试里最常见的一句总结就是：**当前同步代码执行完之后，先清微任务，再看是否进入下一轮宏任务。**

### 追问 3：为什么 `Promise.then` 往往比 `setTimeout` 更早执行？

因为 `Promise.then` 属于微任务，而 `setTimeout` 属于宏任务。
当前这轮同步代码执行完后，Event Loop 会先把微任务清空，再去取下一个宏任务。
所以哪怕 `setTimeout(fn, 0)` 看起来是“立刻执行”，通常也会晚于当前轮次里的 `Promise.then`。

### 追问 4：Event Loop 和页面渲染是什么关系？

这是前端面试里很关键的一点。
浏览器一般不会在每执行一行 JS 后就立刻渲染，而是更常见地在“当前任务执行完、微任务清空后”的某个渲染机会里统一做一次渲染。
所以你可以把它理解成：Event Loop 负责安排“JS 什么时候跑”，渲染流水线负责在合适时机把“最终 DOM 状态”变成像素，这两者是在主线程上交替配合的。
如果主线程一直被长任务占着，或者微任务链过长，哪怕 DOM 已经改了，页面也可能迟迟不刷新，所以 Event Loop 的调度节奏会直接影响页面流畅度。

### 追问 5：Event Loop、渲染流水线和 VDOM 批量更新到底是什么关系？

这个问题我会先拆成两层来说。
第一层是框架层批处理。React、Vue 这类框架通常不会每次状态一变就立刻把每个节点同步改到真实 DOM，而是先把同一轮里的多次变更收集起来，在内存里做计算，得到最终需要提交的 DOM 变更集。
第二层是浏览器层批处理。真实 DOM 被改了之后，浏览器通常也不会每改一个节点就立刻重新做 `Layout` 和 `Paint`，而是先把这些改动记下来，等当前任务和微任务跑完，在这次渲染机会里统一做 `Style -> Layout -> Paint -> Composite`。

如果按时间线理解，通常是这样：

- 同一轮任务里触发了多次状态更新或响应式数据变化。
- 框架把这些变化合并，算出最终哪些真实 DOM 需要变。
- 到提交阶段，框架一次性把这一批 DOM 变更写入真实 DOM。
- 当前宏任务结束后，微任务继续清空。
- 浏览器拿到这一次渲染机会，再基于“已经更新后的 DOM”统一做样式计算、布局、绘制和合成。
- 用户这一帧看到的，是这一整批变更之后的最终结果。

所以你问“VDOM 的一次性渲染是在什么阶段”，更准确的说法不是“VDOM 在某个渲染阶段直接把页面画出来了”，而是：

- `VDOM` 或响应式系统主要发生在框架调度和 DOM 提交阶段。
- 真正把内容画到屏幕上的，仍然是浏览器后面的渲染流水线。
- 之所以看起来像“一次性渲染了所有节点变更”，是因为框架把 DOM 更新做了批处理，浏览器又把渲染做了批处理，这两个批处理叠在一起了。

再补一句容易加分的细节：

- 不同框架把“何时提交 DOM”放在的调度点不完全一样，有的更偏微任务，有的会结合自己的调度器；但共同点都是尽量避免“状态一变就立刻同步改 DOM、同步重排、同步重绘”。
- 但如果代码里中途强制读取布局信息，比如 `offsetWidth`、`getBoundingClientRect()`，浏览器可能为了返回最新结果而提前做布局计算，这时候批处理收益就会被打断。

### 追问 6：`requestAnimationFrame` 和 Event Loop 有什么关系？

我会说，`requestAnimationFrame` 的回调是在浏览器下一次重绘前执行的，它和纯粹的任务队列不太一样，更像是和渲染节奏绑定的调度点。
所以做动画时它通常比 `setTimeout` 更稳，因为它更贴近浏览器真实的刷新节奏。
这也是为什么我们讲 Event Loop 时，经常会顺手带到渲染时机和动画优化。

### 追问 7：Node.js 的 Event Loop 和浏览器是一样的吗？

核心思想一样，都是调度同步和异步任务。
但 Node.js 没有浏览器渲染这一层，而且它的事件循环阶段划分更细，比如 timers、poll、check 等。
所以面试里如果岗位偏前端，我一般先讲浏览器版本；如果继续追问，再补 Node.js 差异。

## 可举的项目例子

如果面试官让我结合项目讲，我一般会这么说：

- 我们排查过一个页面交互延迟的问题，现象是接口已经回来了，但按钮状态和列表刷新总是慢一拍。
- 后来发现不是接口本身慢，而是主线程上堆了很多同步逻辑和微任务，导致渲染时机被往后推了。
- 优化时我们做了两件事：减少不必要的同步计算，把部分更新拆开处理；另外动画和视觉更新尽量放到更贴近渲染节奏的方式里。
- 这个问题的核心就是：理解 Event Loop 之后，你会知道“代码已经跑完”和“用户已经看到更新”不是一回事。

## 易踩坑

- 不要把 Event Loop 说成“异步 API”，它本质是调度机制，不是某一个具体接口。
- 不要只背“宏任务、微任务”这两个词，最好顺手解释清楚执行顺序。
- 不要把 `setTimeout(fn, 0)` 理解成真正的立即执行。
- 不要把“DOM 已经更新”和“用户已经看到更新”混为一谈，中间还隔着浏览器渲染流水线。
- 不要把框架的批量更新简单说成“一定发生在微任务阶段”，不同框架调度细节不完全一样，重点是“合并变更、统一提交”。
- 不要忽略浏览器渲染时机和强制同步布局，前端面试里这往往是加分点。
- 如果提到 Node.js，记得说明它和浏览器 Event Loop 场景不同，不要混着讲。
