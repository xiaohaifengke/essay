# Interview Answer Writer

## Overview

- 处理当前仓库里的面试准备 Markdown。
- 将目标文件名（去掉 `.md`）视为面试题本身。
- 默认处理 `面试准备/` 下的文件；也可以处理用户明确指定的其他 Markdown。
- 优先输出适合真实面试口述的精炼回答，不写成百科式长文。

## Workflow

1. 读取目标文件，先根据文件名识别题目。
2. 判断文件是否为空。
3. 文件为空时，按固定结构直接写入。
4. 文件已有内容时，不要直接改；先给出“拟新增 / 拟修改预览”，等用户确认后再动手。
5. 如果用户只要求补追问、补案例或压缩措辞，也遵守同样的空/非空规则。

## Output Structure

统一使用以下结构：

```markdown
## 回答

## 面试官追问

## 可举的项目例子

## 易踩坑
```

### `## 回答`

- 先给 30~90 秒可直接口述的版本。
- 默认写成 4~8 个要点，结论前置。
- 优先回答“是什么 / 为什么 / 怎么做 / 取舍”。
- 少写背景铺垫，少写教材化定义。

### `## 面试官追问`

- 默认给 3~5 组高频追问。
- 追问优先覆盖：为什么、怎么做、取舍、指标、踩坑、项目案例。
- 每个追问下的回答控制在 2~4 句，先短答，再给展开空间。
- 如果用户要求“继续追问”，在现有追问后延续，不重复前面内容。

### `## 可举的项目例子`

- 优先写可迁移、可替换的项目讲法。
- 不要编造用户没有提供的个人经历、业务数据或项目背景。
- 如果题目明显依赖个人经历，先向用户补问 1 个最关键事实，再生成。

### `## 易踩坑`

- 用 3~5 条短提示提醒常见答偏点。
- 优先提示：定义过长、只讲概念不讲取舍、缺项目例子、把理想方案说成唯一方案。

## Style Rules

- 以口语化、可复述为第一优先级。
- 尽量用短句、要点、转折词，不堆术语。
- 能一句话讲清的内容，不扩成一段。
- 如果必须写定义，定义后立刻补场景和取舍。
- 优先给面试里“能说出口”的版本，而不是“写得很全”的版本。

需要更细的措辞约束时，读取 `references/style-guide.md`。

## Special Cases

### 自我介绍 / 项目亮点 / 项目难点

- 这类题强依赖个人背景。
- 先问 1 个最关键的问题，再生成内容。
- 问题优先级：岗位方向 > 项目经历 > 目标公司 > 时间限制。

### 原理题

- 优先输出：定义、使用场景、优缺点、工程上的落地经验。
- 避免只背概念。

### 工程实践题

- 优先输出：问题背景、方案、取舍、指标或结果。
- 如果没有真实指标，用“可观察结果”替代，不要硬编数字。

## Editing Safety

当文件已有内容时，先给预览，建议使用这种格式：

```markdown
当前文件已有内容，我先给出拟调整方案：
- 拟保留：...
- 拟新增：...
- 拟改写：...

如果你确认，我再实际修改文件。
```

未获得确认前，不要改动非空文件。

## Examples

- “使用 `$interview-answer-writer`，为 `面试准备/monorepo 架构的优势是什么？.md` 生成答案。”
- “使用 `$interview-answer-writer`，先预览你准备如何补充 `面试准备/自我介绍.md`，不要直接改。”
- “使用 `$interview-answer-writer`，继续给这个题补 3 轮面试官追问。”
